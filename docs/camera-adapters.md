# Разработка адаптеров камер

Общий контракт находится в `server/src/cameras/adapter.ts`. Реестр выбирает адаптер автоматически. Специализированные реализации идут раньше общего ONVIF: `server/src/index.ts`.

## Когда нужен отдельный адаптер

Сначала проверьте камеру общим `LibOnvifAdapter`. Создавайте отдельный адаптер только для подтверждённых отличий модели или семейства:

- нестандартный ONVIF port или ответ capabilities;
- отдельный источник динамика, как `tapo://`;
- особые правила PTZ Timeout;
- несовместимый формат событий или media profiles.

Не копируйте общий ONVIF-адаптер целиком. Оборачивайте или расширяйте его, как `TapoC520wsAdapter`.

## Контракт

Реализация `CameraAdapter` содержит:

- стабильные `id` и `displayName`;
- `probe(conn)` для device info, capabilities, profiles и diagnostics;
- `open(conn)` для долгоживущей `CameraSession`.

`CameraSession` закрывает media sources, audio capture, PTZ, presets и события. Метод `close()` освобождает подписки и соединения.

Бросайте `AdapterNotApplicableError`, если устройство точно принадлежит другому адаптеру. Возвращайте диагностику пользователю без пароля и RTSP userinfo. Используйте `safeCameraMessage` на границе ошибки.

`unknown` не означает `supported`. Переводите capability в `supported` только после подтверждения устройством или проверки.

## Ограничения

- Не возвращайте полный RTSP URL через API или diagnostics.
- Не сохраняйте пароль в fixtures и логах.
- Не запускайте FFmpeg с аргументами из данных камеры или пользователя.
- Ограничивайте сетевые операции timeout.
- Отменяйте подписки и timers в `close()`.
- Не блокируйте probe других адаптеров бесконечной попыткой.
- Не расширяйте Caddy allowlist до управляющего API go2rtc.

## Unit-тесты и fixtures

Используйте `node:test`. Примеры находятся в:

- `server/test/adapter-registry.test.ts`;
- `server/test/adapter.test.ts`;
- `server/test/tapo-adapter.test.ts`;
- `server/test/cameras.test.ts`.

Fixture содержит только необходимый фрагмент ONVIF/SOAP/SDP. Перед commit удалите:

- username, password, nonce и session credentials;
- RTSP userinfo;
- токены и cookies;
- серийные номера и MAC-адреса;
- внешние hostnames и tunnel URLs;
- точный домашний адрес и другие личные данные.

Используйте documentation IP ranges `192.0.2.0/24`, `198.51.100.0/24` и `203.0.113.0/24`. Не заменяйте fixture так, чтобы тест потерял особенность устройства.

Проверьте минимум:

1. Выбор нужного адаптера и отказ для чужой модели.
2. Нормализацию profiles и capabilities.
3. Media sources без утечки в публичную модель.
4. Ошибки и timeout.
5. Особенности PTZ, events или audio, ради которых создан адаптер.
6. Повторный reconnect и cleanup.

## Реальное устройство

Unit-тесты не подтверждают физическую совместимость. Выполните проверки из `docs/specs/90-test-strategy.md`, раздел 5. Запишите точную модель, firmware и результаты в `docs/compatibility.md`.

Используйте:

- `PASS` — проверка завершилась успешно;
- `FAIL` — проверка выявила ошибку;
- `NOT_RUN` — проверку не выполняли;
- `BLOCKED` — устройство или условие не позволяют выполнить проверку;
- `UNSUPPORTED` — устройство явно не поддерживает функцию.

Не переносите результат на другую модель или всю линейку производителя.

## Порядок PR

1. Создайте Issue через форму «Камера и совместимость».
2. Приложите очищенные diagnostics и опишите отличие от общего ONVIF.
3. Добавьте минимальную реализацию и тесты.
4. Запустите проверки из `CONTRIBUTING.md`.
5. Укажите результаты реального устройства и оставшиеся `NOT_RUN`.
