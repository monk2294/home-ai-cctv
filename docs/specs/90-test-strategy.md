# 90. Стратегия проверок

## 1. Принципы

- Каждое требование FR-01–FR-13 имеет хотя бы одну проверку. Для этапа 2 каждое S2-FR-01–S2-FR-08 имеет проверку T-18–T-25 из `50-stage-2.md`.
- Проверка должна давать воспроизводимый результат и сохранять фактический вывод.
- Симулятор подтверждает логику платформы, но не подтверждает совместимость конкретной камеры.
- WebRTC, HLS и OpenTunnel проверяются через реальный браузер и сетевой путь.
- Нельзя объявлять требование выполненным только по наличию кода.
- Отсутствие целевого оборудования помечает проверку `BLOCKED`, а не `PASS`.
- Тестовые пароли и токены не должны быть реальными секретами владельца.

Статусы проверки:

- `PASS` — проверка выполнена и критерий соблюдён;
- `FAIL` — проверка выполнена и критерий нарушен;
- `BLOCKED` — проверку нельзя выполнить, указана причина;
- `NOT_RUN` — проверка ещё не выполнялась.

## 2. Уровни тестов

### Unit

Проверяют:

- валидацию PTZ;
- таймеры и generation token PTZ;
- UUIDv4 камер и AUTOINCREMENT event ID без переиспользования;
- RFC 3339 UTC timestamps и совпадение `X-Request-ID` с телом ошибки;
- state machine камеры, включая `disabled` и отличие от `offline`;
- нормализацию ONVIF-событий;
- дедупликацию;
- retention событий;
- очистку URL и логов;
- права session и Bearer-токена;
- лимиты JPEG и MJPEG;
- лимиты WAV duration/capture и audio upload;
- playback registry, Stop и cleanup;
- `audio_output` capability и безопасную модель `AiCamera`;
- маппинг ошибок.

### Integration

Используют:

- ONVIF simulator;
- тестовый RTSP source H.264 с PCMU или PCMA;
- отдельный RTSP source H.264 с AAC;
- реальный go2rtc зафиксированной версии;
- временную SQLite;
- реальный Caddy config для route/auth tests;
- в этапе 2 — FFmpeg/ffprobe, тестовые WAV/MP3 и RTSP source с подтверждённым audio backchannel.

Проверяют контракт между процессами, а не только mocks внутри сервера.

### Web E2E

Проверяют:

- login/logout;
- мастер добавления;
- список и настройки;
- доступность кнопок по capabilities;
- плеер и fallback;
- PTZ pointer/keyboard lifecycle;
- SSE reconnect;
- очистку соединений при уходе со страницы;
- в этапе 2 — mobile viewport, snapshot scheduler, microphone lifecycle и файловый playback.

### Проверки на реальном оборудовании

Нужны как минимум:

- одна камера с H.264 и звуком;
- одна камера с ONVIF motion events;
- одна камера с PTZ и пресетами;
- в этапе 2 — реальная Tapo с ONVIF audio backchannel и динамиком;
- в этапе 2 — Android Chrome и iOS Safari для мобильной приёмки.

Одна модель может закрывать несколько ролей. Модель, firmware и дату нужно записать в матрицу совместимости.

## 4. Детализация критичных проверок

### 4.1 PTZ timer

Нужны отдельные тесты:

1. Move → ручной Stop до истечения срока.
2. Move → автоматический Stop после срока.
3. Move A → Move B → срабатывание таймера A.
4. Move → потеря ONVIF → ограниченный таймаут Stop.
5. Move с нулевыми скоростями → validation error.
6. Move при `unsupported` → `409`.
7. Закрытие страницы → Stop best effort.

В тесте 3 таймер A не должен останавливать команду B.

### 4.2 MJPEG resources

Нужно измерить:

- число FFmpeg-процессов до подключения;
- число процессов при одном consumer;
- ответ `409 AI_STREAM_LIMIT_REACHED` второму consumer без нового FFmpeg-процесса;
- число процессов после disconnect;
- отсутствие записи кадров на диск;
- фактический FPS и размер кадра.

Превышение одного активного транскодера на камеру является дефектом. Второй consumer не разделяет response и не создаёт дополнительный источник.

### 4.3 Disabled и reconnect

Нужно проверить:

1. Disable во время WebRTC/HLS закрывает media stream и subscriptions.
2. Disable во время PTZ отправляет Stop best effort.
3. Disable во время MJPEG закрывает consumer и останавливает транскодер.
4. Snapshot, playback, MJPEG и reconnect для `disabled` возвращают `409 CAMERA_DISABLED`.
5. История событий для `disabled` остаётся доступной.
6. Update настроек `disabled` камеры не запускает сеть.
7. Enable запускает одну попытку Reconciliation.
8. Два ручных reconnect подряд не оставляют две ONVIF-задачи или два subscription.
9. Restart после аварийного preview не оставляет `probe_`-потоки.

### 4.4 SSE и reconnect

Нужно проверить:

- heartbeat проходит через Caddy и OpenTunnel;
- proxy не отправляет события пачкой после буферизации;
- после reconnect клиент повторно читает REST events;
- дубликаты удаляются по ID;
- закрытие вкладки завершает generator;
- 10 циклов reconnect не создают 10 независимых EventSource.

### 4.5 WebRTC/HLS cleanup

После пяти переходов между камерами:

- нет старых `RTCPeerConnection`;
- нет старых signaling WebSocket;
- нет старых HLS loaders;
- число media consumers возвращается к ожидаемому;
- звук не воспроизводится из фонового элемента.

## 5. Матрица совместимости камер

Для каждого устройства заполнять:

| Поле | Значение |

| ONVIF | Результат probe |

## 6. Матрица браузеров

Обязательный минимум MVP:

- актуальный стабильный Chrome или Chromium на desktop;
- актуальный стабильный Firefox на desktop.

Этап 2 добавляет:

- актуальный стабильный Chrome на Android;
- актуальный стабильный Safari на iOS;
- viewport sizes из `50-stage-2.md` §5.1 для layout regression.

Нативный HLS Safari, WebRTC, микрофон и autoplay проверяются на реальных мобильных браузерах. До прогона статус — `NOT_RUN`; при отсутствии устройства — `BLOCKED`. Эмуляция viewport не даёт `PASS` для мобильного браузера.

## 7. Нагрузочный профиль T-17

Расчётный профиль:

- 4 доступных RTSP-источника;
- 2 одновременных зрителя;
- 1 MJPEG consumer на камеру при тесте предельного профиля;
- 2 FPS и ширина 640 для MJPEG по умолчанию;
- включённые ONVIF subscriptions;
- периодические события движения;
- обычный polling веб-клиента;
- в этапе 2 — два главных экрана с JPEG polling раз в секунду на видимую доступную камеру;
- в этапе 2 — периодические WAV capture и последовательные audio playback с проверкой cleanup.

Собирать каждые 60 секунд:

- CPU по контейнеру;
- RSS памяти;
- число процессов и threads;
- число file descriptors;
- число активных media consumers;
- число FFmpeg-процессов;
- ошибки reconnect;
- задержку события от simulator до SSE;
- дисковое использование SQLite и logs.

Если целевой сервер недоступен, тест на другой машине фиксирует только её конфигурацию и не подтверждает NFR-01 для целевого сервера.

## 8. Security checks

Минимальный список:

- Повторить API без cookie и Bearer.
- Повторить AI endpoints с admin cookie и admin endpoints с AI Bearer. Каждый маршрут принимает только назначенный режим, кроме явно документированных исключений.
- Проверить истёкшую и удалённую сессию.
- Проверить logout.
- Проверить `X-Request-ID` на успешных и ошибочных ответах и совпадение с `request_id` ошибки.
- Проверить `Origin` мутирующих запросов.
- Проверить отсутствие wildcard CORS.
- Проверить недоступность go2rtc root, streams и config editor.
- Проверить, что stream name не позволяет задать source URL или FFmpeg arguments.
- Проверить request body limits, включая 64 КиБ для обычных API и 5 МиБ только для audio/play.
- Проверить, что audio API не принимает URL, FFmpeg arguments, дополнительные поля и Cookie/Bearer не своего режима.
- Проверить, что internal audio resource недоступен через Caddy.
- Проверить rate limit login.
- Проверить cookie attributes под HTTPS.
- Сканировать API responses и logs на тестовые секреты.

## 9. OpenTunnel evidence

Для T-15 сохранить:

- название и версию tunnel;
- схему портов без токенов;
- внешний hostname в masked form, если владелец считает его чувствительным;
- поддержку HTTPS, WSS, SSE, HLS и MJPEG;
- поддержку TCP/UDP mappings;
- результат WebRTC;
- время непрерывного теста;
- обрывы и reconnect;
- ограничения тарифа или продукта, если они влияют на работу.

Если tunnel не поддерживает WebRTC media, HLS может закрыть удалённый просмотр. При этом удалённый WebRTC помечается `UNSUPPORTED_BY_TUNNEL`, а не `PASS`.

## 10. Критерии готовности MVP

MVP готов, когда:

1. T-01–T-14 имеют `PASS`.
2. T-15 имеет `PASS` для обязательного HLS-сценария через выбранный OpenTunnel.
3. T-16 имеет `PASS`.
4. T-17 имеет `PASS` на целевом сервере либо владелец явно принял отклонение по оборудованию.
5. Реальная PTZ-камера подтвердила T-05 и T-06.
6. Все `FAIL` устранены или явно выведены за границы MVP изменением спецификации.
7. Нет неучтённых `BLOCKED` для обязательных требований.
8. Документация и OpenAPI соответствуют фактической реализации.

## 11. Критерии готовности этапа 2

Используй `50-stage-2.md` §12 и §15. T-18–T-25 обязательны. Реальная Tapo подтверждает T-20. Отсутствие мобильного устройства или камеры даёт `BLOCKED`, а не `PASS`. Все регрессии T-01–T-17 повторяются после изменений.
