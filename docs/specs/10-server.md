# 10. Сервер

Связанные требования: FR-01–FR-13, NFR-04, NFR-06–NFR-11, S2-FR-02–S2-FR-08. Целевые правила этапа 2 — в `50-stage-2.md`.

## 1. Назначение

Сервер управляет камерами, авторизацией, ONVIF, PTZ, событиями и API для ИИ. Он хранит конфигурацию в SQLite и управляет потоками go2rtc через внутренний HTTP API.

Сервер не декодирует обычный видеопоток для браузера и не реализует собственную детекцию движения.

## 2. Технические решения

- Node.js 22 LTS. Точная patch-версия фиксируется в `.nvmrc` и Docker image.
- TypeScript в strict mode для сервера и общих контрактов.
- Fastify как HTTP-фреймворк.
- JSON Schema и Ajv через Fastify для валидации запросов и ответов.
- Drizzle ORM, `better-sqlite3` и версионированные миграции Drizzle.
- SQLite в режиме WAL.
- Встроенный `fetch`/Undici с `AbortSignal` для HTTP-запросов к go2rtc.
- Реестр адаптеров камер за общим TypeScript-интерфейсом. Адаптер выбирается автоматическим перебором: специализированный Tapo C520WS, затем общий ONVIF.
- Пакет `argon2` и алгоритм Argon2id для пароля администратора.
- Встроенный `node:crypto` и AES-256-GCM для секретов камер.
- OpenAPI 3.0.3 в `contracts/api-v1.openapi.yaml`.
- `openapi-typescript` для генерации типов сервера и React-клиента из одного контракта.
- npm workspaces и `package-lock.json` для фиксации зависимостей монорепозитория.

Выбор ONVIF-библиотеки должен подтвердить интеграционный тест. Реализация использует пакет `onvif` (agsh/onvif, Promise API). Бизнес-логика не должна зависеть напрямую от классов этой библиотеки. Долгие ONVIF- и media-операции используют асинхронный I/O. Синхронные транзакции `better-sqlite3` должны быть короткими и не блокировать event loop ожиданием сети.

## 4. Модель камеры

### 4.1 Данные конфигурации

Сервер хранит:

- UUID камеры;
- уникальное имя;
- host или IP;
- ONVIF port;
- включённое состояние;
- username камеры;
- зашифрованный password камеры;
- зашифрованный RTSP override, если он задан;
- ONVIF profile token;
- возможности камеры;
- состояние подключения;
- последнюю ошибку;
- timestamps создания, изменения и последнего успешного подключения.

API никогда не возвращает password, RTSP credentials или RTSP override.

### 4.2 Идентификаторы, время и request ID

- `camera_id` является UUIDv4. Сервер генерирует ID, клиент не выбирает его.
- Внутренний event ID использует SQLite `INTEGER PRIMARY KEY AUTOINCREMENT`. API сериализует его как строку.
- Все timestamps API используют RFC 3339 в UTC с суффиксом `Z`.
- `received_at` отражает серверные часы. `occurred_at` использует валидное время камеры или `received_at`, если камера не предоставила время.
- Каждый HTTP API response содержит `X-Request-ID`. Он совпадает с `request_id` в теле ошибки.
- Reverse proxy передаёт существующий `X-Request-ID` или позволяет серверу создать новый. Сервер принимает только 1–128 символов `A–Z`, `a–z`, `0–9`, `.`, `_` или `-`. Невалидное значение заменяется новым ID.
- Request ID не содержит пользовательские секреты и используется в логах.

### 4.3 Состояния

| Состояние | Условие |
|---|---|
| `disabled` | Администратор отключил камеру. Сервер не поддерживает ONVIF-подключения, подписки и media stream |
| `connecting` | Идёт первичное подключение, переподключение или применение настроек |
| `online` | ONVIF и выбранный медиапрофиль доступны |
| `degraded` | Камера доступна, но ONVIF, медиапоток или отдельная функция не работают |
| `offline` | Включённая камера не отвечает на попытки подключения |

Поле `last_error` объясняет последний отказ. Состояние возможности не должно зависеть только от общего состояния камеры. Для `disabled` сервер возвращает последние известные capabilities, но не перепроверяет их до включения.

`offline` всегда означает техническую недоступность. Пользовательское отключение использует только `disabled`.

### 4.4 Возможности

Каждая возможность имеет одно из значений:

- `supported` — камера подтвердила функцию;
- `unsupported` — камера сообщила об отсутствии функции;
- `unknown` — проверка не завершилась или ONVIF-ответ не позволяет сделать вывод.

Сервер определяет:

- видео;
- входящий звук (`audio`);
- передачу звука на динамик (`audio_output`, этап 2);
- события движения;
- Continuous Move;
- пресеты PTZ.

Клиент не должен считать `unknown` равным `supported`.

## 5. Добавление камеры

### 5.1 Probe

`POST /api/v1/cameras/probe` выполняет проверку без сохранения камеры.

Сервер должен:

1. Проверить поля и ограничить время подключения.
2. Подключиться к ONVIF с учётом смещения времени камеры, если библиотека это требует.
3. Получить информацию об устройстве.
4. Получить media profiles.
5. Получить capabilities и события.
6. Получить кодеки и разрешения доступных профилей. В этапе 2 проверить ONVIF backchannel по `50-stage-2.md`, не блокируя Probe при ошибке этой проверки.
7. Проверить RTSP override, если пользователь его задал. Разрешён только scheme `rtsp://`. Userinfo в URL запрещён: сервер использует отдельные username и password. Максимальная длина URL — 2048 символов.
8. Вернуть профили и возможности без RTSP-URL.
9. Завершить временные подключения.

Probe не создаёт постоянный поток и не сохраняет пароль. Для тестового снимка мастер вызывает `POST /api/v1/cameras/probe/snapshot.jpg` с теми же параметрами подключения и выбранным `profile_token`. Сервер создаёт временный поток go2rtc со случайным именем `probe_<random>` и TTL не более 30 секунд. Блок `finally` удаляет поток сразу после ответа или ошибки. Фоновая очистка удаляет поток, если основной запрос завершился аварийно. Reconciliation удаляет все оставшиеся `probe_`-потоки после restart сервера. Реализация не сохраняет временный секрет в логах и БД.

### 5.2 Create

`POST /api/v1/cameras` сохраняет конфигурацию после выбора профиля.

Сервер должен:

1. Проверить лимит `MAX_CAMERAS`, по умолчанию 4 камеры. Отключённые камеры также входят в лимит.
2. Убрать внешние пробелы имени и проверить его уникальность без учёта регистра. Username и password не нормализуются.
3. Для `enabled=true` повторно получить RTSP URI по выбранному профилю или использовать RTSP override. Для `enabled=false` сохранить выбранный profile token без сетевого GetStreamUri.
4. Зашифровать секреты.
5. Сохранить камеру в одной транзакции.
6. Для `enabled=true` создать или обновить поток go2rtc.
7. Для `enabled=true` запустить ONVIF-подключение и подписки в фоне.
8. Вернуть публичную модель камеры.

Для `enabled=false` сервер пропускает сетевые шаги 3 и 6–7 и возвращает `state=disabled`. При этом Create сохраняет результат предварительного Probe и выбранный профиль. RTSP URI получают при последующем Enable.

Если go2rtc временно недоступен, сервер сохраняет включённую камеру со состоянием `connecting` или `degraded`. Reconciliation повторяет создание потока. Сбой медиашлюза не должен оставлять частично записанные секреты.

### 5.3 Update

При изменении адреса, учётных данных или профиля сервер:

1. Останавливает старые ONVIF-подписки.
2. Переводит камеру в `connecting`.
3. Обновляет конфигурацию и поток go2rtc.
4. Запускает подключение заново.

Пустой password при обновлении означает «оставить прежний». API возвращает только `has_rtsp_override`, но не сам URL. Отсутствие поля `rtsp_url_override` сохраняет прежний override. Строка заменяет его. Для удаления используется только `clear_rtsp_override=true`; значение `null` не разрешено. Одновременная передача `rtsp_url_override` и `clear_rtsp_override=true` возвращает `400 VALIDATION_ERROR`.

Изменение настроек отключённой камеры сохраняет конфигурацию без подключения и оставляет `state=disabled`.

Переход `enabled=true → false`:

1. Переводит камеру в `disabled` и запрещает новые media/PTZ-команды.
2. Отправляет PTZ Stop best effort при активном движении. В этапе 2 останавливает audio playback и WAV capture.
3. Отменяет ONVIF-подписки и таймеры.
4. Закрывает MJPEG и удаляет media stream.
5. Сохраняет события и последние известные capabilities.

Переход `enabled=false → true` переводит камеру в `connecting` и запускает Reconciliation для этой камеры.

### 5.4 Delete

Сервер должен:

1. Запретить новые команды камере.
2. Остановить PTZ best effort.
3. Отменить таймеры и ONVIF-подписки.
4. Закрыть MJPEG и другие активные AI-запросы этой камеры. В этапе 2 остановить audio playback и WAV capture.
5. Удалить поток go2rtc.
6. Удалить запись камеры, события и секреты из БД.

Если go2rtc недоступен, сервер удаляет запись и добавляет имя потока в очередь очистки. Reconciliation удаляет осиротевший поток при следующем успешном соединении.

### 5.5 Ручной reconnect

`POST /api/v1/cameras/{camera_id}/reconnect` перезапускает подключение без изменения сохранённых секретов.

- Операция доступна только для `enabled=true`.
- Для `disabled` сервер возвращает `409 CAMERA_DISABLED`.
- Сервер отменяет старые ONVIF-задачи, subscriptions и PTZ-таймеры.
- Сервер закрывает активный MJPEG consumer и удаляет его транскодер. В этапе 2 также останавливает audio playback и WAV capture.
- Сервер переводит камеру в `connecting` и запускает Reconciliation для одной камеры.
- Повторный вызов во время reconnect заменяет прежнюю попытку и не создаёт параллельные задачи.
- Ответ содержит актуальную публичную модель камеры.

## 6. ONVIF Events

### 6.1 Проверка поддержки

Сервер использует ONVIF capabilities и Event Properties, чтобы определить доступные события. Наличие ONVIF само по себе не означает поддержку движения.

Если камера не сообщает свойства событий, сервер устанавливает `motion_events=unknown` и пытается создать подписку. Результат подписки уточняет диагностику, но не должен менять `unknown` на `supported` до получения подтверждения соответствующего события или явного описания топика.

### 6.2 Подписка

Предпочтительный механизм MVP — PullPointSubscription. Адаптер должен:

- создать подписку;
- вызывать PullMessages с ограниченным таймаутом;
- продлевать подписку до истечения срока;
- обрабатывать начало и конец движения;
- пересоздавать подписку после ошибки;
- ограничивать частоту попыток exponential backoff с jitter;
- использовать максимальный интервал повтора 60 секунд.

Адаптер должен распознавать стандартные ONVIF-топики движения и эквивалентные сообщения, подтверждённые эталонной камерой. Неизвестный топик нельзя считать движением только из-за наличия слова `motion` без теста или явного правила.

### 6.3 Нормализованное событие

Событие содержит:

- монотонно возрастающий строковый ID в пределах сервера;
- `camera_id`;
- тип `motion`;
- состояние `active` или `inactive`;
- `occurred_at` от камеры или время получения при отсутствии времени;
- `received_at`;
- источник `onvif`;
- исходный topic.

Сервер не хранит полный XML по умолчанию. Дедупликация использует SHA-256 от канонической комбинации camera ID, topic, состояния, времени сообщения и source message ID, если камера его предоставила. Колонка `dedup_hash` имеет unique constraint. Повторная доставка PullMessages завершается без новой записи и без повторной SSE-отправки.

Вставка события и удаление старых записей сверх `EVENT_RETENTION_PER_CAMERA` выполняются в одной транзакции. По умолчанию лимит равен 1000 на камеру. Event ID не переиспользуется после retention или удаления других камер.

### 6.4 SSE

`GET /api/v1/events` отправляет новые события всем авторизованным администраторам.

- Формат: `text/event-stream`.
- Поле `id` содержит ID события.
- Поле `event` содержит `camera-event`.
- Поле `data` содержит JSON события.
- Heartbeat отправляется не реже одного раза в 15 секунд.
- Reverse proxy не буферизует поток.
- При переподключении клиент заново запрашивает список последних событий через REST.
- Отключение клиента отменяет server-side generator.

## 7. PTZ

### 7.1 Continuous Move

`POST /api/v1/cameras/{camera_id}/ptz/move` принимает `pan`, `tilt`, `zoom` и `duration_ms`.

Правила:

- Каждая скорость находится в диапазоне от `-1` до `1`.
- Хотя бы одна скорость отличается от нуля.
- `duration_ms` находится в диапазоне от 100 до 5000.
- Значение по умолчанию — 1000 мс.
- Сервер проверяет `ptz_continuous=supported`.
- Сервер передаёт Timeout камере и сам планирует Stop на тот же срок.
- Новая Move отменяет прежний таймер остановки.
- Таймер старой команды не должен остановить новую команду. Для этого используется generation token или эквивалент.
- HTTP-клиент не повторяет Move автоматически.

### 7.2 Stop

`POST /api/v1/cameras/{camera_id}/ptz/stop`:

- отменяет активный таймер;
- отправляет ONVIF Stop для осей, которые поддерживает профиль;
- возвращает `409 CAMERA_UNAVAILABLE`, если камера недоступна;
- не сообщает об успешной остановке до ответа камеры, кроме отдельно описанной ошибки таймаута.

При завершении работы сервер отправляет Stop активным камерам best effort. Завершение процесса не должно ждать недоступную камеру дольше настроенного короткого таймаута.

### 7.3 Пресеты

Сервер получает пресеты через ONVIF и возвращает только token и name. Команда GotoPreset использует token из пути. Сервер проверяет принадлежность token текущему профилю или повторно получает список перед выполнением. Token нормализуется к строке: отдельные модели (Tapo C520WS) отдают числовой token, контракт API требует строку. Пустой список пресетов на камере с PTZ означает «пресеты не сохранены», а не отсутствие поддержки: Tapo публикует пресеты в ONVIF после создания их в приложении Tapo.

Создание, изменение и удаление пресетов не входит в MVP.

## 8. Авторизация

### 8.1 Администратор

- Единственный username — `admin`.
- Первичный пароль читается из файла секрета при создании БД.
- Смена файла секрета после bootstrap не меняет пароль автоматически.
- Пароль хранится только в виде Argon2id hash.
- Session token содержит не менее 256 бит энтропии.
- SQLite хранит только SHA-256 hash session token.
- Cookie называется `homecctv_session` и имеет `HttpOnly`, `SameSite=Strict` и `Path=/`.
- Cookie получает `Secure` при работе через HTTPS.
- Сессия истекает через 12 часов. Активность продлевает срок не более чем до 24 часов от входа.
- Logout удаляет сессию на сервере.

`GET /api/v1/auth/verify` предназначен для `forward_auth` reverse proxy. Он возвращает `204` для действующей администраторской сессии и `401` иначе.

### 8.2 ИИ-агент

- Bearer-токен содержит не менее 256 бит энтропии и читается из отдельного файла секрета.
- Сравнение токена выполняется за постоянное время.
- Токен даёт доступ только к `/api/v1/ai/*` и публичному liveness.
- В MVP токен не даёт доступа к CRUD, PTZ, событиям и администраторской сессии.
- В этапе 2 токен разрешает только AI PTZ, AI audio playback, WAV и discovery по `50-stage-2.md`. CRUD, admin PTZ, admin events и администраторская сессия остаются закрытыми.
- AI Bearer имеет физическое управление камерой в этапе 2. Веб-клиент не получает этот токен.
- Токен нельзя передавать в query string.

### 8.3 Защита API

- CORS по умолчанию отключён.
- Мутирующие cookie-запросы проверяют `Origin`, если браузер его отправил.
- Неверный логин и неверная сессия возвращают одинаковый общий `401` без раскрытия причины.
- Сервер ограничивает число неудачных попыток входа по IP и времени.
- Глобальный HTTP limit по умолчанию принимает 1200 запросов на IP в минуту. `HTTP_RATE_LIMIT_PER_MINUTE` меняет значение. Превышение возвращает 429 `RATE_LIMIT_EXCEEDED` в общей схеме `Error`. Отдельный login limit сохраняет 5 ошибок за 5 минут.

## 9. Медиа-API

Для `state=disabled` snapshot, playback и MJPEG возвращают `409 CAMERA_DISABLED`. История событий остаётся доступной. Для остальных состояний сервер может попытаться получить media, но обязан соблюдать конечный timeout.

### 9.1 JPEG для ИИ

`GET /api/v1/ai/cameras/{camera_id}/snapshot.jpg`:

- проверяет Bearer-токен;
- принимает необязательную ширину от 64 до 1920;
- запрашивает кадр у go2rtc;
- возвращает `image/jpeg` с `Cache-Control: no-store`;
- не возвращает RTSP-URL;
- возвращает `503 CAMERA_MEDIA_UNAVAILABLE`, если кадр нельзя получить за настроенный таймаут.

### 9.2 JPEG для администратора

`GET /api/v1/cameras/{camera_id}/snapshot.jpg`:

- проверяет администраторскую сессию;
- принимает необязательную ширину от 64 до 1920;
- использует тот же внутренний запрос к go2rtc, что и JPEG для ИИ;
- возвращает `image/jpeg` с `Cache-Control: no-store`;
- не требует и не возвращает Bearer-токен ИИ;
- применяет тот же таймаут и коды ошибок, что JPEG для ИИ.

Этот endpoint используют карточки камер и диагностика веб-клиента.

### 9.3 MJPEG для ИИ

`GET /api/v1/ai/cameras/{camera_id}/stream.mjpeg`:

- проверяет Bearer-токен;
- возвращает `multipart/x-mixed-replace`;
- использует 2 FPS по умолчанию;
- ограничивает FPS значением 5;
- использует ширину 640 по умолчанию;
- ограничивает ширину значением 1280;
- разрешает только один активный MJPEG consumer на камеру;
- создаёт не более одного активного MJPEG-транскодера на камеру;
- возвращает `409 AI_STREAM_LIMIT_REACHED` второму consumer без создания нового транскодера;
- не добавляет звук;
- отключает транскодер после disconnect единственного consumer;
- освобождает ресурсы при shutdown и отключении камеры.

MVP не разделяет один MJPEG HTTP response между несколькими ИИ-агентами. При необходимости нескольких consumers требование нужно изменить отдельно.

MJPEG не предназначен для удалённого просмотра администратором.

### 9.4 Playback descriptors

`GET /api/v1/cameras/{camera_id}/playback`:

- проверяет администраторскую сессию;
- возвращает хотя бы один доступный режим или `503 CAMERA_MEDIA_UNAVAILABLE`;
- выбирает `preferred=webrtc`, если доступны оба режима;
- выбирает `preferred=hls`, если WebRTC не настроен;
- возвращает только same-origin relative URLs;
- не использует публичные long-lived media tokens;
- полагается на проверку admin session для каждого signaling, playlist и segment request.

`null` для WebRTC или HLS означает, что режим не настроен. Оба поля не могут быть `null` в успешном ответе.

### 9.5 API этапа 2

`50-stage-2.md` и OpenAPI 1.1 определяют AI discovery, конечный WAV, AI PTZ и файловое воспроизведение. Admin и AI playback используют общий `AudioOutputService` и общий busy-лимит. Сервер не принимает внешние media URL и не сохраняет аудиоархив.

## 10. Reconciliation

После запуска сервер:

1. Выполняет миграции.
2. Загружает включённые камеры.
3. Создаёт или обновляет потоки go2rtc только для включённых камер.
4. Удаляет осиротевшие `cam_`-потоки и все оставшиеся `probe_`-потоки.
5. Проверяет, что отключённые камеры не имеют активных `cam_`-потоков.
6. Запускает ONVIF-подключения только для включённых камер.
7. Восстанавливает подписки на события только для включённых камер.

Reconciliation идемпотентен. Повторный запуск не создаёт дубликаты потоков и подписок.

Одна задача Reconciliation не должна последовательно ждать недоступные камеры дольше общего дедлайна. Подключения к разным камерам выполняются независимо.

## 11. Хранение

Минимальный набор таблиц:

| Таблица | Содержимое |
|---|---|
| `cameras` | Публичную конфигурацию, зашифрованные секреты, профиль и состояние |
| `camera_events` | AUTOINCREMENT ID, нормализованные события, unique `dedup_hash` и индексы по камере и ID |
| `admin_users` | Имя и Argon2id hash единственного администратора |
| `admin_sessions` | Hash токена и сроки действия |
| `media_cleanup` | Очередь удаления потоков go2rtc |

Секреты камеры шифруются через AES-256-GCM. Ключ содержит 32 байта и хранится в base64. Каждая операция использует новый случайный nonce длиной 12 байт. SQLite хранит nonce, ciphertext, authentication tag и версию шифра. Миграции не выводят значения этих полей в лог.

SQLite использует:

- WAL;
- `foreign_keys=ON`;
- bounded busy timeout;
- миграции до запуска HTTP-трафика.

## 12. Ошибки

Все ошибки API, кроме медиаданных и SSE после начала потока, используют схему `Error` из OpenAPI.

| HTTP | Примеры кодов |
|---|---|
| 400 | `VALIDATION_ERROR`, `INVALID_PROFILE` |
| 401 | `UNAUTHORIZED` |
| 403 | `FORBIDDEN` |
| 404 | `CAMERA_NOT_FOUND`, `PRESET_NOT_FOUND`, `AUDIO_PLAYBACK_NOT_FOUND` |
| 409 | `CAMERA_LIMIT_REACHED`, `DUPLICATE_CAMERA_NAME`, `CAPABILITY_UNSUPPORTED`, `CAMERA_UNAVAILABLE`, `CAMERA_DISABLED`, `AI_STREAM_LIMIT_REACHED`, `AI_AUDIO_LIMIT_REACHED`, `AUDIO_OUTPUT_BUSY` |
| 413 | `AUDIO_TOO_LARGE` |
| 415 | `UNSUPPORTED_AUDIO_FORMAT` |
| 422 | Ошибка JSON Schema/Ajv-валидации, `CAMERA_ADAPTER_NOT_DETECTED`, `INVALID_AUDIO` или `AUDIO_DURATION_LIMIT_EXCEEDED` в единой обёртке `Error` |
| 429 | `TOO_MANY_LOGIN_ATTEMPTS`, `RATE_LIMIT_EXCEEDED` |
| 502 | `ONVIF_UPSTREAM_ERROR`, `MEDIA_UPSTREAM_ERROR` |
| 503 | `CAMERA_MEDIA_UNAVAILABLE`, `MEDIA_GATEWAY_UNAVAILABLE` |
| 504 | `ONVIF_TIMEOUT`, `MEDIA_TIMEOUT` |

Поле `message` предназначено для диагностики администратором. Оно не содержит секреты и не должно копировать необработанный ответ внешней библиотеки без очистки.

## 13. Логи и healthcheck

### Логи

- Использовать structured logging.
- Добавлять `request_id`, `camera_id`, операцию и результат.
- Не логировать тело login, probe, create и update.
- Очищать userinfo и query credentials из URL.
- Не логировать Authorization и Cookie.
- Не логировать JPEG, WAV и другие бинарные медиаданные. Не логировать тела audio upload и временные internal audio URL.

### Healthcheck

- `/api/v1/health/live` проверяет только работоспособность HTTP-процесса.
- `/api/v1/health/ready` проверяет доступность SQLite и завершение миграций. Endpoint доступен только внутри Docker-сети; Caddy не публикует его.
- Недоступность одной камеры не делает сервер неработоспособным.
- Недоступность go2rtc отражается в readiness как отдельный компонент, но не раскрывает внутренние URL.
