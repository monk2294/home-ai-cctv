## 2. Границы этапа

### Входит

- Адаптивный SPA для смартфонов и планшетов.
- Chrome на Android и Safari на iOS в матрицу приёмки.
- ONVIF Profile T audio backchannel через существующий go2rtc.
- Микрофон браузера в режиме push-to-talk.
- Файловое воспроизведение для администратора и ИИ.
- Ограниченные WAV-фрагменты для ИИ.
- PTZ для ИИ через отдельные Bearer-маршруты.

### Не входит

- Нативное мобильное приложение и push-уведомления.
- Постоянная запись звука, архив аудио и библиотека загруженных файлов.
- Встроенный TTS, распознавание речи и серверный анализ звука.
- Проигрывание произвольных HTTP- или RTSP-URL от клиента.
- Проприетарный `tapo://` протокол, облачная учётная запись Tapo и новые облачные секреты.
- Несколько администраторов, RBAC и отдельные scope для AI Bearer.
- PTZ-туры, редактирование пресетов и непрерывное движение сверх 5 секунд.
- Гарантия микрофона через текущий OpenTunnel. Туннель не переносит WebRTC media.
- Автоматический перенос микрофона в HLS. HLS не принимает исходящий звук.

## 3. Архитектурные решения

| ID | Решение | Причина |
|---|---|---|
| S2-D-01 | Использовать ONVIF Profile T RTSP backchannel через go2rtc | Единый протокол уже применяется для видео |
| S2-D-02 | Разделить `audio` и `audio_output` | Микрофон и динамик камеры являются разными возможностями |
| S2-D-03 | Передавать микрофон только в активном WebRTC-плеере | go2rtc поддерживает двусторонний звук через WebRTC |
| S2-D-04 | Передавать аудиофайл сырым HTTP body на сервер | Один контракт подходит браузеру и ИИ без multipart |
| S2-D-05 | Хранить загруженный звук только в памяти сервера | Этап не создаёт аудиоархив |
| S2-D-06 | Давать go2rtc временный внутренний URL на загруженный буфер | go2rtc FFmpeg может читать источник без общего volume |
| S2-D-07 | Отдавать ИИ конечный WAV, а не бесконечный поток | Агент получает файл для STT или анализа без WebRTC-клиента |
| S2-D-08 | Запускать FFmpeg и ffprobe в контейнере server | Сервер контролирует длительность, формат и время жизни процессов |
| S2-D-09 | Зеркалировать PTZ под `/api/v1/ai/*` и использовать общий `PtzService` | Сохраняются авторизация, лимиты и generation token |
| S2-D-10 | Не открывать новые публичные endpoint-ы go2rtc | Caddy сохраняет узкий allowlist |

### 3.1 Обязательный эксперимент до основной реализации

Сначала выполни T-20 на реальной Tapo C520WS:

1. Зафиксируй модель и firmware.
2. Проверь RTSP `DESCRIBE` с `Require: www.onvif.org/ver20/backchannel`.
3. Найди в SDP направление `audio/sendonly` и список кодеков динамика.
4. Проверь микрофон и WAV через go2rtc 1.9.9.
5. Запиши фактический кодек и результат в `compatibility.md`.

Если go2rtc 1.9.9 не поддерживает рабочий backchannel этой камеры, проверь новый стабильный релиз на отдельном стенде. Зафиксируй новую версию и повтори T-03, T-04, T-09, T-10 и T-15. Не используй `latest` или `master`.

Если камера принимает звук только через `tapo://`, останови эту ветку реализации. Добавление облачного пароля требует отдельного решения владельца.

## 4. Возможность `audio_output`

`CameraCapabilities` получает обязательное поле `audio_output` со значениями `supported`, `unsupported`, `unknown`.

- `audio` описывает приём звука с микрофона камеры.
- `audio_output` описывает передачу звука на динамик камеры.
- `supported` требует SDP с ONVIF backchannel и аудиокодеком, который поддерживает go2rtc.
- `unsupported` означает завершённую проверку без backchannel или явный отказ `Unsupported`.
- `unknown` означает timeout, ошибку связи или неполный ответ камеры.
- Наличие ONVIF DeviceIO без SDP не доказывает `supported`.
- Состояние возможности относится к выбранному профилю. Смена профиля запускает новую проверку.
- После обновления существующие камеры получают `audio_output=unknown` до первой проверки. Отсутствие поля в старом JSON не является ошибкой БД.
- Для `disabled` сохраняется последний известный результат по общему правилу capabilities.
- Probe может использовать первый совместимый профиль для предварительной проверки. Create и Reconciliation уточняют результат выбранного профиля.
- Ошибка проверки `audio_output` не блокирует видео, входящий звук и сохранение камеры.

Сервер может создать временный `probe_`-поток и прочитать безопасную диагностику go2rtc для проверки. Публичные ответы не содержат SDP, RTSP-URL или учётные данные.

Клиент включает микрофон и файловое воспроизведение только при `audio_output=supported`. При `unknown` клиент показывает «Передача звука не подтверждена». При `unsupported` клиент показывает «Камера не поддерживает передачу звука».

## 5. Мобильная адаптация

### 5.1 Целевые размеры

Проверяй как минимум:

- 320×568;
- 360×800;
- 390×844;
- 768×1024;
- landscape на реальном смартфоне.

Эти размеры не являются жёсткими breakpoints. Выбирай breakpoints по наложению контента.

### 5.2 Каркас и навигация

- При узком экране sidebar заменяется компактной верхней панелью.
- Панель содержит бренд, ссылки «Камеры» и «События», кнопку выхода.
- Не добавляй скрытое меню, если все элементы помещаются без него.
- Основной контент использует одну колонку на смартфоне.
- Карточки камер, плеер, PTZ, события и настройки не выходят за viewport.
- Детальный экран размещает плеер перед PTZ и событиями.
- Учитывай `safe-area-inset-*` у закреплённых элементов.
- Используй `100dvh` с fallback, если высота viewport влияет на раскладку.

### 5.3 Элементы управления

- Интерактивная область имеет размер не менее 44×44 CSS px.
- Поля ввода используют font-size не менее 16 px на iOS.
- Панели плеера и PTZ переносят элементы на новую строку без наложений.
- Длинные имена, ошибки и тексты событий обрезаются или переносятся без горизонтального скролла.
- Диалог удаления помещается по ширине и имеет собственную вертикальную прокрутку.
- Экранная клавиатура не скрывает активное поле и основную кнопку submit.
- Если Fullscreen API недоступен, клиент скрывает кнопку fullscreen.
- PTZ сохраняет `pointercancel`, pointer capture и Stop при отпускании.
- `touch-action: none` применяется только к элементам движения, не ко всей странице.

### 5.4 Мобильные браузеры

- Проверь текущие стабильные Chrome на Android и Safari на iOS.
- Проверь WebRTC, нативный HLS Safari, звук камеры и микрофон по HTTPS.
- Эмуляция viewport в Firefox проверяет только раскладку. Она не заменяет реальные мобильные браузеры.
- Отсутствие устройства даёт соответствующей проверке статус `BLOCKED`.

## 6. Обновление снимков раз в секунду

### 6.1 Планировщик

Для главного экрана действуют правила:

1. Используй `GET /api/v1/cameras/{id}/snapshot.jpg?width=640`.
2. Запускай polling для карточек `online` и `degraded`, которые находятся в viewport.
3. Целевой период запуска — 1000 мс на карточку при успешных ответах.
4. Не создавай параллельные запросы для одной карточки. Медленный запрос пропускает следующие тики.
5. Не ставь накопившиеся тики в очередь.
6. При `document.visibilityState !== 'visible'` останавливай таймеры и отменяй запросы.
7. При выходе карточки из viewport останавливай её polling.
8. При размонтировании главного экрана отменяй все таймеры и запросы.
9. `disabled`, `connecting` и `offline` не запускают polling.
10. Смена состояния камеры пересоздаёт только затронутый polling.

### 6.2 Отображение и ошибки

- Успешный ответ атомарно заменяет текущий JPEG.
- Не показывай loader и не очищай прежний кадр между успешными ответами.
- Старый ответ не должен заменить более новый кадр.
- При использовании object URL освобождай прежний URL после замены и при размонтировании.
- Ошибка сохраняет последний успешный кадр и показывает ненавязчивую диагностику.
- Abort при скрытии, уходе из viewport и размонтировании не считается ошибкой снимка.
- После ошибки повторяй запрос не чаще одного раза в 5 секунд до восстановления.
- `401` завершает администраторскую сессию по общему правилу клиента.
- `409 CAMERA_DISABLED` останавливает polling без повторных запросов.

### 6.3 Нагрузка

- Не создавай отдельный RTSP source для polling.
- Сервер объединяет совпадающие по камере и ширине in-flight запросы к go2rtc.
- Допустим memory cache JPEG не более 250 мс. Cache-Control публичного ответа остаётся `no-store`.
- Постоянный дисковый кэш запрещён.
- T-17 дополняется двумя главными экранами с активным 1-секундным polling.

## 7. Передача звука на камеру

### 7.1 Микрофон администратора

Управление находится на детальном экране рядом с громкостью. Используй режим «Удерживайте, чтобы говорить».

Условия доступности:

- камера включена;
- `audio_output=supported`;
- фактический режим плеера — WebRTC;
- браузер имеет `navigator.mediaDevices.getUserMedia`;
- страница открыта в secure context.

Поведение:

1. При создании PeerConnection используй audio transceiver `sendrecv` вместо `recvonly`.
2. Запрашивай разрешение на микрофон только после действия пользователя.
3. Добавляй микрофонный track через `replaceTrack` без повторного SDP offer.
4. До нажатия исходящий track отсутствует. Браузер не передаёт микрофон в фоне.
5. Если кнопку отпустили до ответа на разрешение, не добавляй track и останови полученные tracks.
6. На время речи отключай входящий звук этой камеры, чтобы ограничить акустическую обратную связь.
7. После отпускания вызови `replaceTrack(null)` и останови все локальные tracks.
8. Восстанови прежние mute и volume после окончания речи.
9. Запрашивай `echoCancellation`, `noiseSuppression` и `autoGainControl`, если браузер их поддерживает.

Немедленно прекрати речь при:

- `pointerup`, `pointercancel` или потере pointer capture;
- `keyup` клавиши активации;
- истечении 60 секунд непрерывной речи;
- скрытии вкладки;
- размонтировании экрана;
- logout или Disable;
- разрыве WebRTC;
- переходе в HLS или смене режима плеера.

Ошибка разрешения показывает сообщение и не перезапускает плеер. При HLS покажи «Говорить можно только через WebRTC». При HTTP по LAN покажи требование HTTPS или localhost. Не используй автоматический retry для микрофона.

### 7.2 Файловое воспроизведение

Администратор выбирает локальный файл на детальном экране. ИИ передаёт файл тем же способом через свой Bearer-маршрут.

Ограничения:

- MIME: `audio/wav` или `audio/mpeg`;
- максимум 5 МиБ;
- максимум 30 секунд декодированного звука;
- хотя бы одна декодируемая аудиодорожка;
- видео и дополнительные дорожки не используются;
- внешние URL запрещены;
- одно активное файловое воспроизведение на камеру для администратора и ИИ вместе.

Сервер проверяет размер, MIME и результат ffprobe. Проверка клиента только улучшает UX и не заменяет серверную проверку.

Жизненный цикл:

1. Сервер читает body с жёстким лимитом.
2. Сервер проверяет камеру, capability и отсутствие активного playback.
3. ffprobe определяет формат и длительность.
4. Сервер сохраняет bytes только в памяти и создаёт случайный внутренний resource ID.
5. Внутренний HTTP-маршрут отдаёт буфер по случайному resource ID только внутри Docker backend.
6. Caddy не проксирует этот маршрут.
7. Сервер вызывает go2rtc Stream to camera с FFmpeg source и `#input=file`.
8. go2rtc выбирает codec из фактического backchannel. Для Tapo проверь PCMA/8000 mono в T-20.
9. Сервер возвращает `202` и модель `AudioPlayback` после принятия команды go2rtc.
10. Сервер освобождает буфер и внутренний resource после Stop или по таймеру `estimated_end_at + 5 секунд`. Этот таймер также снимает busy-лимит после штатной длительности файла.

`AudioPlayback.estimated_end_at` является оценкой по длительности файла. Ответ `202` не доказывает физическое воспроизведение звука. Эту проверку выполняет T-20 или T-22 на камере.

`DELETE` по playback ID останавливает активное воспроизведение через go2rtc с пустым `src` и освобождает ресурсы. Неизвестный или завершённый ID возвращает `404 AUDIO_PLAYBACK_NOT_FOUND`.

Disable, Delete, reconnect, shutdown и смена профиля сначала останавливают активное воспроизведение этой камеры. Restart не восстанавливает прошлые аудиофайлы.

UI показывает выбранное имя файла, длительность, состояние отправки и кнопку Stop. Не сохраняй файл в IndexedDB, localStorage или sessionStorage. Ошибка не блокирует видео.

### 7.3 Маршруты

Точные тела и ответы определяет OpenAPI.

| Операция | Администратор | ИИ |
|---|---|---|
| Начать playback | `POST /api/v1/cameras/{camera_id}/audio/play` | `POST /api/v1/ai/cameras/{camera_id}/audio/play` |
| Остановить playback | `DELETE /api/v1/cameras/{camera_id}/audio/play/{playback_id}` | `DELETE /api/v1/ai/cameras/{camera_id}/audio/play/{playback_id}` |

Оба семейства маршрутов вызывают общий `AudioOutputService`. Cookie не принимается на AI-маршрутах. Bearer не принимается на admin-маршрутах.

## 8. Звук камеры для ИИ

`GET /api/v1/ai/cameras/{camera_id}/audio.wav` возвращает новый конечный фрагмент текущего звука.

Параметр `duration_ms`:

- значение по умолчанию — 5000;
- минимум — 1000;
- максимум — 15000.

Формат ответа:

- `Content-Type: audio/wav`;
- PCM signed 16-bit little-endian;
- mono;
- 16000 Hz;
- `Cache-Control: no-store`;
- корректный WAV header и фактический размер данных.

Правила реализации:

1. Используй внутренний RTSP-канал go2rtc для существующего `cam_`-потока.
2. FFmpeg читает только звук и пишет WAV в stdout.
3. Сервер собирает не более 500 КиБ полезного WAV на максимальном запросе.
4. Не сохраняй фрагмент в SQLite или на диск.
5. Заверши FFmpeg после заданной длительности.
6. Убей процесс при disconnect клиента, shutdown, Disable, Delete и reconnect камеры.
7. Разрешай один активный capture на камеру и не более двух capture на сервер.
8. Второй capture той же камеры получает `409 AI_AUDIO_LIMIT_REACHED`.
9. Если звук не появился за 5 секунд запуска, верни `503 CAMERA_MEDIA_UNAVAILABLE`.
10. Не возвращай `200` с частичным WAV после ошибки источника.

Для `audio=unsupported` сервер возвращает `409 CAPABILITY_UNSUPPORTED`. Для `disabled` — `409 CAMERA_DISABLED`. Метод не меняет выбранный профиль и не включает отключённую камеру.

## 9. PTZ и обнаружение камер для ИИ

### 9.1 Маршруты PTZ

| Операция | AI-маршрут |
|---|---|
| Move | `POST /api/v1/ai/cameras/{camera_id}/ptz/move` |
| Stop | `POST /api/v1/ai/cameras/{camera_id}/ptz/stop` |
| Список пресетов | `GET /api/v1/ai/cameras/{camera_id}/ptz/presets` |
| GotoPreset | `POST /api/v1/ai/cameras/{camera_id}/ptz/presets/{preset_token}/goto` |

Маршруты используют те же схемы и поведение, что admin PTZ:

- скорости от `-1` до `1`;
- хотя бы одна ненулевая скорость;
- `duration_ms` от 100 до 5000;
- общий таймер Stop и generation token;
- проверка capabilities и состояния камеры;
- проверка принадлежности пресета профилю;
- отсутствие автоматического retry Move.

AI и admin команды используют один `PtzService` и одну ONVIF-сессию камеры. Новая Move любого клиента отменяет прежний таймер по существующим правилам.

### 9.2 Список и состояние камер

Добавь:

- `GET /api/v1/ai/cameras`;
- `GET /api/v1/ai/cameras/{camera_id}`.

Модель `AiCamera` содержит только:

- `id`;
- `name`;
- `state`;
- `capabilities`;
- безопасный `last_error`.

Модель не содержит `host`, `onvif_port`, `username`, `profile_token`, RTSP override, секреты и внутренние stream names.

## 10. Авторизация и ошибки

- Все новые AI-маршруты требуют только AI Bearer.
- AI guard выполняется на `onRequest`, до чтения и валидации большого body.
- Все новые admin-маршруты требуют только admin session.
- Мутирующие admin-запросы сохраняют проверку `Origin`.
- Bearer и session token запрещены в query string.
- AI Bearer теперь разрешает физическое движение камеры и звук. Не передавай его веб-клиенту.
- CRUD камер, admin events и admin session остаются недоступными для AI Bearer.
- Каждый ответ содержит `X-Request-ID` по общему правилу.

Новые ошибки:

| HTTP | Код | Условие |
|---|---|---|
| 409 | `AUDIO_OUTPUT_BUSY` | На камере уже активно файловое воспроизведение |
| 409 | `AI_AUDIO_LIMIT_REACHED` | Превышен лимит одновременных WAV capture |
| 404 | `AUDIO_PLAYBACK_NOT_FOUND` | Playback ID не найден или уже завершён |
| 413 | `AUDIO_TOO_LARGE` | Body превышает 5 МиБ |
| 415 | `UNSUPPORTED_AUDIO_FORMAT` | MIME не входит в allowlist |
| 422 | `INVALID_AUDIO` | FFmpeg не распознаёт аудиодорожку |
| 422 | `AUDIO_DURATION_LIMIT_EXCEEDED` | Длительность превышает 30 секунд |

Существующие `CAMERA_DISABLED`, `CAMERA_UNAVAILABLE`, `CAPABILITY_UNSUPPORTED`, `MEDIA_TIMEOUT` и `MEDIA_UPSTREAM_ERROR` сохраняют смысл. Текст ошибки не содержит bytes звука, internal URL, RTSP, Cookie или Authorization.

## 11. Reverse proxy и развёртывание

### Caddy

- Сохрани общий JSON body limit 64 КиБ.
- Для двух маршрутов `audio/play` задай body limit 5 МиБ с небольшим техническим запасом только при необходимости HTTP-фреймворка.
- Не увеличивай лимит остальных `/api/v1/*`.
- Измени `Permissions-Policy` на `microphone=(self)` для same-origin SPA.
- Сохрани `camera=()` и `geolocation=()`.
- Не добавляй внутренний audio resource в маршруты Caddy.
- Не расширяй media allowlist для Stream to camera. Сервер вызывает go2rtc напрямую.

### Server image

- Добавь FFmpeg с ffprobe в production image server.
- Зафиксируй версии пакетов согласно правилам репозитория.
- Запускай процессы без shell и без строк команд от клиента.
- Передавай только фиксированные аргументы и серверные resource URL.
- Ограничивай время запуска, длительность, stdout и число процессов.

### OpenTunnel

- WAV для ИИ и файловое воспроизведение работают через обычный HTTPS и входят в повторный T-15.
- Микрофон требует рабочий WebRTC media.
- Текущий OpenTunnel не переносит WebRTC media. Поэтому удалённый микрофон получает `UNSUPPORTED_BY_TUNNEL` до появления TURN или TCP/UDP mapping.
- Не блокируй удалённое файловое воспроизведение из-за недоступности микрофона.

## 15. Критерии готовности этапа

Этап готов, когда:

1. Четыре требования владельца имеют подтверждённые проверки.
2. T-18–T-25 имеют `PASS` на обязательном оборудовании.
3. T-01–T-17 не имеют новых `FAIL`.
4. Реальная Tapo подтверждает микрофон и файловое воспроизведение.
5. Нет `BLOCKED` для обязательных сценариев без явного решения владельца.
6. OpenAPI, generated types и реализация совпадают.
7. `npm test`, `npm run typecheck` и `npm run build` завершаются успешно.
8. Документация фиксирует фактические ограничения мобильных браузеров и OpenTunnel.
