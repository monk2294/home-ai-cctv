# 11. Медиашлюз go2rtc

Связанные требования: FR-01–FR-03, FR-08–FR-11, NFR-01–NFR-05, NFR-09, NFR-10, NFR-12.

## 1. Назначение

go2rtc получает RTSP-потоки камер и предоставляет:

- WebRTC для основного просмотра;
- HLS для резервного просмотра;
- JPEG для администратора и ИИ;
- MJPEG для ИИ;
- переключение и повторное подключение к источникам;
- транскодирование звука и MJPEG через FFmpeg, если это необходимо.

Сервер управляет потоками. Веб-клиент не изменяет конфигурацию go2rtc напрямую.

## 2. Версия и запуск

- Использовать официальный Docker image go2rtc с зафиксированной стабильной версией.
- Зафиксировать digest после проверки конкретного релиза.
- Не использовать `latest` или `master`.
- FFmpeg нужен внутри образа для звука и MJPEG.
- Обновление версии требует повторения тестов T-03, T-04, T-09, T-10 и T-15.

В go2rtc задаётся `api.base_path: /media`. Внутренние и внешние HTTP API используют префикс `/media/api/`. Это позволяет go2rtc формировать корректные относительные HLS URL и не требует rewrite в Caddy.

## 3. Именование и жизненный цикл потока

Имя потока:

```text
cam_<camera_uuid_without_hyphens>
```

Пример формата без реальных данных:

```text
cam_0123456789abcdef0123456789abcdef
```

Только сервер создаёт имена. Пользователь не задаёт имя потока. Временные preview-потоки используют имя `probe_<random>` и TTL не более 30 секунд. Они не являются камерами и не попадают в публичный список playback.

### Создание

Сервер передаёт go2rtc:

- RTSP-URL выбранного профиля;
- учётные данные камеры внутри защищённого канала управления;
- дополнительный источник FFmpeg для звука, если браузер не поддерживает исходный кодек;
- дополнительный источник MJPEG по запросу API ИИ.

### Обновление

При изменении камеры сервер обновляет соответствующий поток. Операция должна быть идемпотентной.

### Удаление

Сервер удаляет поток при удалении или отключении камеры. При недоступности go2rtc запись попадает в очередь `media_cleanup`. Ручной reconnect пересоздаёт подключение к существующему `cam_`-потоку без изменения его имени.

### Восстановление

После запуска сервер сравнивает включённые камеры и потоки go2rtc. Он создаёт отсутствующие и удаляет осиротевшие потоки с префиксом `cam_`. Также он удаляет все оставшиеся `probe_`-потоки и потоки отключённых камер. Чужие потоки без префиксов `cam_` и `probe_` удалять запрещено.

## 4. RTSP

- Использовать TCP interleaved transport, если эталонная камера стабильно работает через TCP.
- Не создавать отдельный RTSP source для каждого браузера.
- Настроить reconnect при обрыве.
- Не включать постоянную запись.
- Не публиковать RTSP-сервер go2rtc на host.
- Не передавать RTSP-URL в браузер и API ошибок.
- Не записывать RTSP userinfo в логи go2rtc. Если версия go2rtc выводит source URL, ограничить доступ к логам и снизить уровень логирования.

Если камера требует UDP RTSP, адаптер может включить его для конкретной камеры после отдельной проверки. Единый глобальный переход на UDP не требуется.

## 5. Кодеки

| Тип | Поддержка MVP | Поведение |
|---|---|---|
| H.264 | Обязательная | Без видеотранскодирования в расчётном профиле |
| H.265 | Не гарантирована | Показывать ошибку кодека или результат отдельной проверки |
| PCMU | Обязательная проверка | WebRTC может использовать совместимый аудиокодек |
| PCMA | Обязательная проверка | WebRTC может использовать совместимый аудиокодек |
| AAC | Обязательная проверка | Использовать совместимый контейнер или транскодировать звук для WebRTC |
| Opus | Допустимо | Использовать для WebRTC после транскодирования |

Правила:

- Не транскодировать H.264 только для смены контейнера.
- Транскодировать звук один раз на общий источник камеры, а не отдельно для каждого зрителя.
- Не запускать видеотранскодер H.265 → H.264 в MVP без нового расчёта ресурсов.
- Сообщать `audio=unknown`, если ONVIF не дал сведения, а фактический RTSP SDP ещё не проверен.
- После подключения медиашлюза диагностика может уточнить фактические кодеки.

## 6. WebRTC

### Сигнализация

Браузер использует относительный WSS/WS URL через reverse proxy:

```text
/media/api/ws?src=<stream_name>
```

Reverse proxy проверяет администраторскую сессию до проксирования. Браузер не получает доступ к `/media/api/streams`.

### Медиаданные

- go2rtc использует `8555/tcp` и `8555/udp`.
- WebRTC media не проходит через обычный HTTP-туннель.
- В локальной сети публикуются оба порта, если клиент и сервер находятся в совместимой сети.
- Docker candidate configuration содержит адрес сервера, а не внутренний Docker IP.
- Нельзя фильтровать единственный рабочий Docker interface без проверки кандидатов.
- Удалённый WebRTC требует отдельного TCP/UDP tunnel или TURN.
- При отсутствии такого канала HLS остаётся обязательным рабочим режимом.

### Конфигурация кандидатов

Развёртывание должно позволять задать:

- LAN address сервера;
- внешний hostname;
- внешний порт;
- STUN;
- TURN URL, username и credential при наличии.

TURN-сервер не входит в состав MVP Docker Compose.

Выбранный OpenTunnel переносит только HTTPS/TCP 443: внешний hostname, внешний порт, STUN и TURN для WebRTC не настраиваются; удалённый режим — HLS (спецификация 30 §8.3, T-15). Возврат к этим параметрам возможен только при замене туннеля на вариант с TCP/UDP mappings.

## 7. HLS

Браузер получает относительный playlist URL:

```text
/media/api/stream.m3u8?src=<stream_name>&mp4
```

Требования:

- Reverse proxy разрешает playlist и связанные segment routes.
- Плейлист не кешируется публично.
- Запросы сегментов проверяют ту же администраторскую сессию.
- Браузер использует нативный HLS там, где он поддерживается.
- Остальные целевые браузеры используют `hls.js`.
- Переход на HLS не требует повторного входа.
- Остановка плеера закрывает загрузку playlist и сегментов.

Перед приёмкой необходимо зафиксировать фактические segment routes выбранной версии go2rtc в конфигурации reverse proxy. Нельзя заменять точечный allowlist проксированием всего `/media/api/`.

## 8. JPEG

Внутренний endpoint go2rtc:

```text
/media/api/frame.jpeg?src=<stream_name>
```

Использование:

- мастер добавления получает временный снимок;
- администратор получает снимок через серверный endpoint;
- ИИ получает снимок через AI endpoint;
- ширина передаётся через параметры go2rtc, если она задана;
- сервер не кеширует снимок дольше заданного короткого TTL.

Постоянный дисковый кэш JPEG не входит в MVP. Допустим только memory cache для предотвращения одновременных одинаковых запросов.

## 9. MJPEG

Внутренний endpoint go2rtc:

```text
/media/api/stream.mjpeg?src=<stream_name>
```

Если источник не содержит MJPEG, go2rtc использует FFmpeg.

Ограничения:

- 2 FPS по умолчанию;
- максимум 5 FPS;
- ширина 640 по умолчанию;
- максимальная ширина 1280;
- один активный MJPEG consumer на камеру;
- один активный MJPEG-транскодер на камеру;
- второй consumer получает `409 AI_STREAM_LIMIT_REACHED` от сервера до создания источника;
- транскодер останавливается после disconnect единственного потребителя;
- звук не добавляется.

Сервер передаёт параметры FPS и размера в конфигурацию FFmpeg source. Query string публичного MJPEG не должен позволять произвольные аргументы FFmpeg.

## 10. Разрешённые endpoint-ы

### Доступ через reverse proxy

Reverse proxy проксирует только:

- `/media/api/ws` для WebRTC signaling;
- `/media/api/webrtc`, если выбранная реализация плеера использует SDP endpoint;
- `/media/api/stream.m3u8`;
- связанные HLS playlist и segment routes.

Все эти запросы требуют администраторскую сессию.

### Доступ только серверу

- `/media/api/streams` и управление источниками;
- `/media/api/frame.jpeg`;
- `/media/api/stream.mjpeg`;
- диагностические API, необходимые серверу.

### Запрещено извне

- корневая панель go2rtc;
- редактор конфигурации;
- `/media/api/streams`;
- произвольные `exec` и `echo` sources;
- произвольные HTTP, FFmpeg и RTSP URLs из query string браузера.

## 11. Сетевая изоляция

- HTTP API go2rtc слушает только внутреннюю Docker-сеть.
- Host не публикует порт `1984`.
- Host не публикует порт `8554`.
- Host публикует `8555/tcp` и `8555/udp` только при включённом WebRTC.
- Reverse proxy и сервер находятся в одной внутренней сети с go2rtc.
- Внешний клиент выбирает только stream name в публичном media endpoint. Он не задаёт source URL.

При настройке `api.allow_paths` необходимо сохранить внутренние endpoint-ы сервера и ограничить остальные. При настройке `exec.allow_paths` разрешить только FFmpeg. Не включать неиспользуемые модули go2rtc.

## 12. Ошибки и восстановление

Медиашлюз считается недоступным при:

- истечении TCP connection timeout;
- истечении HTTP request timeout;
- ошибке создания потока;
- потере процесса или контейнера.

Действия сервера:

- пометить затронутую камеру `degraded`, если ONVIF ещё работает;
- повторить операцию по backoff;
- не перезаписывать конфигурацию камеры;
- не раскрывать внутренний ответ go2rtc клиенту без очистки.

Docker может перезапустить контейнер go2rtc. После его запуска сервер повторяет Reconciliation.

## 13. Наблюдаемость

Сервер периодически проверяет доступность go2rtc и читает только необходимую диагностику.

Для каждой камеры диагностика должна позволять определить:

- существует ли поток;
- подключён ли RTSP source;
- какие кодеки обнаружены;
- есть ли активные consumers;
- запущен ли транскодер.

В production API не возвращает URLs источников и credentials. Логи не содержат Authorization, Cookie и RTSP userinfo.
