# 00. Системная спецификация home-ai-cctv

- Статус: основа для реализации MVP.
- Дата: 2026-11-21.
- Версия API: v1.
- Стек: Node.js, Fastify, React и TypeScript.
- Масштаб: до 4 IP-камер.

## 1. Цель

Система запускается на локальном сервере и подключается к IP-камерам по Wi-Fi или Ethernet. Администратор удалённо смотрит видео, слушает звук, управляет PTZ и получает события движения. ИИ-агент получает JPEG-снимки и MJPEG-поток через HTTP API.

## 2. Границы MVP

### 2.1 Входит

- До 4 камер с ONVIF и RTSP.
- До 2 одновременных зрителей.
- Один MJPEG consumer и один MJPEG-транскодер на камеру.
- Добавление камеры по адресу через веб-интерфейс.
- Проверка ONVIF, получение профилей и возможностей камеры.
- Выбор профиля видео при добавлении.
- WebRTC как основной способ просмотра.
- HLS как резервный способ просмотра.
- Прослушивание звука камеры.
- Continuous Move, Stop и переход к пресетам PTZ.
- Получение событий движения через ONVIF Events.
- Живая лента событий через SSE.
- JPEG и MJPEG для ИИ-агента.
- Один администратор.
- Отдельный Bearer-токен для ИИ-агента.
- Docker Compose и reverse proxy для OpenTunnel.

### 2.2 Не входит

- Запись видео, звука и клипов.
- Двусторонний звук.
- Серверная детекция движения и распознавание объектов.
- Настройка зон и чувствительности детекции на камере.
- Уведомления в мессенджеры и по электронной почте.
- Несколько администраторов и RBAC.
- Автоматический поиск камер через WS-Discovery.
- PTZ-туры, патрулирование и редактирование пресетов.
- Проприетарные API производителей.
- Облачные P2P-протоколы камер.
- Мобильное приложение.
- Отказоустойчивый кластер.
- Гарантированная поддержка H.265.

## 3. Термины

| Термин | Значение |
|---|---|
| Сервер | Node.js-сервис управления камерами, событиями, доступом и API |
| Медиашлюз | Отдельный процесс go2rtc |
| Веб-клиент | SPA для администратора |
| Reverse proxy | Caddy, единственная HTTP-точка входа |
| OpenTunnel | Внешнее средство публикации локального HTTP-сервиса |
| Профиль | ONVIF Media Profile камеры |
| Событие движения | Сообщение камеры об изменении состояния движения |
| Снимок | Один JPEG-кадр без звука |
| MJPEG | Последовательность JPEG-кадров без звука |

## 4. Участники и границы доверия

### Участники

- Администратор использует браузер.
- ИИ-агент использует HTTP API с Bearer-токеном.
- Камера предоставляет ONVIF и RTSP.
- OpenTunnel предоставляет внешний HTTPS-доступ.

### Границы доверия

1. Браузер и ИИ-агент обращаются только к reverse proxy.
2. Reverse proxy передаёт запросы серверу, веб-клиенту и разрешённым endpoint-ам медиашлюза.
3. Сервер обращается к ONVIF-интерфейсу камеры.
4. Медиашлюз обращается к RTSP-интерфейсу камеры.
5. Только сервер и reverse proxy обращаются к HTTP API медиашлюза.
6. Панель управления и RTSP-сервер медиашлюза не доступны извне.
7. WebRTC media идёт отдельно от HTTP reverse proxy.

## 5. Архитектура

```text
                         ┌──────────────────────┐
Браузер ── HTTPS/WSS ──► │ OpenTunnel           │
                         └──────────┬───────────┘
                                    │
                              ┌─────▼──────┐
                              │ Caddy      │
                              └───┬───┬────┘
                                  │   │
                        ┌─────────┘   └──────────┐
                        │                        │
                 ┌──────▼──────┐          ┌──────▼──────┐
                 │ Веб-клиент  │          │ Node.js     │
                 └─────────────┘          └──┬───────┬──┘
                                             │       │
                                      ONVIF  │       │ управление
                                             │       ▼
                                             │   ┌──────────────┐
                                             │   │ go2rtc       │
                                             │   └──────┬───────┘
                                             │          │ RTSP
                                      ┌──────▼──────────▼──────┐
                                      │ IP-камеры              │
                                      └────────────────────────┘

ИИ-агент ── HTTPS ──► Caddy ──► Node.js ──► go2rtc
Браузер ── WebRTC media TCP/UDP ──► go2rtc, если сеть это разрешает
```

Компонентные обязанности описаны в документах `10-server.md`, `11-media-gateway.md`, `20-web-client.md` и `30-reverse-proxy.md`.

## 6. Функциональные требования

| ID | Требование | Критерий приёмки | Проверка |
|---|---|---|---|
| FR-01 | Добавление камеры | Пользователь вводит адрес и учётные данные. Сервер получает профили и возможности. Пользователь видит тестовый снимок до сохранения. | T-01 |
| FR-02 | Список камер | Клиент показывает состояние, снимок, возможности и ошибку подключения каждой камеры. | T-02 |
| FR-03 | Видео и звук | Клиент использует WebRTC или автоматически включает HLS. Пользователь может включить звук. | T-03, T-04 |
| FR-04 | PTZ | Совместимая камера выполняет поворот, наклон, зум и Stop. Сервер ограничивает движение пятью секундами. | T-05 |
| FR-05 | Пресеты PTZ | Клиент получает пресеты и переводит камеру в выбранную позицию. | T-06 |
| FR-06 | События движения | Сервер получает ONVIF-событие, сохраняет метаданные и отправляет событие через SSE. | T-07 |
| FR-07 | Неподдерживаемые функции | Клиент блокирует недоступные команды и показывает состояние возможности. | T-08 |
| FR-08 | JPEG для ИИ | ИИ-агент получает JPEG по HTTP с Bearer-токеном. | T-09 |
| FR-09 | MJPEG для ИИ | ИИ-агент получает MJPEG с заданными FPS и шириной. Сервер отклоняет значения выше лимита. | T-10 |
| FR-10 | Переподключение | После восстановления сети сервер восстанавливает ONVIF-подписки и медиапотоки без перезапуска платформы. | T-11 |
| FR-11 | Изменение и удаление | Сервер применяет новые настройки и удаляет связанные потоки и подписки. | T-12 |
| FR-12 | Авторизация | Анонимный клиент не получает защищённые API, снимки и медиапотоки. | T-13 |

Детали проверок приведены в `90-test-strategy.md`.

## 7. Нефункциональные требования

| ID | Требование |
|---|---|
| NFR-01 | Система поддерживает расчётный профиль: 4 камеры, 2 зрителя и 1 MJPEG consumer на камеру. Фактическую нагрузку проверяют на целевом сервере. |
| NFR-02 | В стабильной локальной сети WebRTC должен обеспечивать задержку не более 2 секунд на эталонной камере. |
| NFR-03 | HLS должен обеспечивать задержку не более 15 секунд на эталонной камере при отсутствии перегрузки сети. |
| NFR-04 | После восстановления доступности камеры сервер должен восстановить подключение не более чем за 60 секунд. |
| NFR-05 | Один RTSP-источник на профиль камеры должен обслуживать несколько потребителей через медиашлюз, если камера и go2rtc поддерживают такой режим. |
| NFR-06 | Система не сохраняет видео и звук. SQLite хранит конфигурацию, сессии и не более 1000 событий на камеру. |
| NFR-07 | Пароли камер шифруются перед записью в SQLite. Пароль администратора хешируется Argon2id. |
| NFR-08 | API и логи не содержат пароли, Bearer-токены, session token и учётные данные из RTSP-URL. |
| NFR-09 | Все длительные соединения имеют таймауты, heartbeat или механизм обнаружения разрыва. |
| NFR-10 | После перезапуска Docker Compose сервер восстанавливает конфигурацию камер и потоки из своей БД. |
| NFR-11 | Ошибка одной камеры не блокирует API и работу остальных камер. |
| NFR-12 | Все образы и зависимости фиксируются версиями. Образ `latest` запрещён. |

## 8. Поддержка протоколов и кодеков

- ONVIF обязателен для проверки возможностей, PTZ и событий.
- RTSP обязателен для видео.
- H.264 входит в обязательную приёмку.
- PCMU, PCMA и AAC входят в проверку звука.
- Медиашлюз может транскодировать звук через FFmpeg.
- Видеотранскодирование не входит в расчётный профиль MVP.
- H.265 можно показывать только после отдельной проверки браузера и камеры. Отсутствие поддержки не является дефектом MVP.
- WebRTC в локальной сети обязателен.
- HLS через OpenTunnel обязателен.
- Удалённый WebRTC зависит от OpenTunnel и проверяется отдельно.

## 9. Модель безопасности

### Аутентификация

- Администратор входит по имени `admin` и паролю.
- Сервер создаёт opaque session token и отправляет его в HttpOnly cookie.
- ИИ-агент использует отдельный Bearer-токен.
- Bearer-токен ИИ не даёт доступа к управлению камерами и PTZ.
- Веб-клиент и API используют один origin.

### Секреты

- Секреты передаются через файлы Docker secrets или файлы с правами `0600`.
- Ключ шифрования камер хранится отдельно от SQLite.
- Резервная копия SQLite не содержит ключ шифрования.
- Для восстановления резервной копии нужны SQLite и ключ шифрования.

### Сетевая поверхность

- Публичный HTTP-доступ открывает только reverse proxy.
- Порт `1984` медиашлюза не публикуется на host.
- Порт `8554` медиашлюза не публикуется на host.
- Порт `8555/tcp` и `8555/udp` публикуется только для WebRTC.
- OpenTunnel не должен заменять авторизацию платформы.
- `/api/v1/health/ready` доступен только внутри Docker-сети.

## 10. Основные решения

| ID | Решение | Причина |
|---|---|---|
| D-01 | Ограничить камеры ONVIF и RTSP | Единый контракт вместо адаптеров производителей |
| D-02 | Использовать Node.js, Fastify, TypeScript и SQLite | Единый язык сервера и клиента, небольшой локальный сервер и простое развёртывание |
| D-03 | Использовать go2rtc | Один медиашлюз для RTSP, WebRTC, HLS, JPEG и MJPEG |
| D-04 | Использовать React, TypeScript и Vite | Типизированный SPA и генерация клиента из OpenAPI |
| D-05 | Использовать Caddy | Единая точка входа и проксирование длительных соединений |
| D-06 | Не реализовывать WS-Discovery в MVP | UDP multicast усложняет Docker-сеть; ручной адрес закрывает добавление камеры |
| D-07 | Хранить только метаданные событий | Архив не входит в MVP |
| D-08 | Не открывать полный API go2rtc | API медиашлюза имеет широкие права |
| D-09 | Использовать SSE для событий | Клиенту нужен односторонний поток без отдельного WebSocket API |
| D-10 | Ограничить PTZ-команду пятью секундами | Снизить риск непрерывного движения после разрыва связи |
