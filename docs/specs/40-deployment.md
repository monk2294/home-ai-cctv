# 40. Развёртывание и эксплуатация

Связанные требования: NFR-01, NFR-06–NFR-12, S2-FR-02–S2-FR-07. Изменения server image и временных аудиобуферов этапа 2 — в `50-stage-2.md`.

## 1. Состав Docker Compose

| Сервис | Образ | Публикуемые порты | Постоянные данные |
|---|---|---|---|
| `proxy` | Caddy с зафиксированной версией | `8080/tcp` | Конфигурация и при необходимости TLS |
| `web` | Собранный SPA и лёгкий static server | Нет | Нет |
| `server` | Собранный Node.js + Fastify image; FFmpeg/ffprobe в этапе 2 | Нет | SQLite и миграции |
| `media` | go2rtc с зафиксированной версией | `8555/tcp`, `8555/udp` при WebRTC | Read-only базовый config |

### MCP (спецификация 60)

| Сервис | Состав | Порты наружу | Состояние |
|---|---|---|---|
| `mcp` | MCP-сервер для ИИ-агентов; AI Bearer-токен из того же secret | Нет (через proxy `/mcp`) | Нет |

Все образы фиксируются версией. Digest фиксируется после проверки релиза. Запрещены `latest`, `master` и незакреплённые dependency ranges в lock-файлах. Версия Node.js фиксируется в `.nvmrc` и Docker image. JavaScript-зависимости фиксируются через `package-lock.json`; production install использует `npm ci`.

## 2. Сети

Предлагаются две Docker-сети:

- `edge`: proxy и web;
- `backend`: proxy, server, media и mcp.

Server и media должны иметь исходящий доступ в LAN камер. Web не должен иметь доступ к управляющему API go2rtc.

Host networking для всего стека не используется. Ручной адрес камеры работает через исходящую Docker-сеть. WS-Discovery не входит в MVP и не требует multicast-настроек.

## 3. Volumes и файлы

Минимальные данные:

```text
server-data/
  home-ai-cctv.db
  home-ai-cctv.db-wal
  home-ai-cctv.db-shm

secrets/
  admin_password
  ai_api_token
  camera_encryption_key

config/
  Caddyfile
  go2rtc.example.yaml
  proxy/ и web/ configuration
```

Правила:

- SQLite volume доступен только контейнеру server.
- Secrets монтируются read-only.
- Файлы секретов имеют права `0600` на host.
- Первичный пароль администратора содержит не менее 12 символов.
- Bearer-токен ИИ генерируется из не менее чем 32 случайных байт и кодируется в base64url.
- Ключ шифрования камер содержит 32 случайных байта в base64 для AES-256-GCM и не копируется в image.
- Базовый go2rtc config монтируется read-only, если выбранный режим управления это позволяет.
- Рабочий `config/go2rtc.yaml` создаёт `scripts/init-secrets.sh` из example с правами `0600` и исключается из репозитория: go2rtc дописывает в него streams с учётными данными камер.
- Медиаархив не создаётся. Этап 2 допускает WAV capture и upload buffer только в памяти server по `50-stage-2.md`; backup их не включает.

## 4. Конфигурация

Минимальный набор параметров:

| Параметр | Назначение |
|---|---|
| `PUBLIC_BASE_URL` | Внешний HTTPS origin |
| `SESSION_COOKIE_SECURE` | Secure cookie для HTTPS |
| `SESSION_SECRET_FILE` или эквивалент | Дополнительный секрет, если реализации нужен signing key |
| `ADMIN_PASSWORD_FILE` | Пароль только для первичного bootstrap |
| `AI_API_TOKEN_FILE` | Bearer-токен ИИ |
| `CAMERA_ENCRYPTION_KEY_FILE` | Ключ секретов камер |
| `DATABASE_PATH` | Путь SQLite внутри server-data |
| `MAX_CAMERAS` | Положительный целый лимит камер, по умолчанию 4 |
| `EVENT_RETENTION_PER_CAMERA` | Положительный целый лимит событий на камеру, по умолчанию 1000 |
| `MEDIA_API_BASE_URL` | Внутренний URL go2rtc |
| `WEBRTC_LAN_CANDIDATE` | LAN IP сервера для WebRTC |
| `WEBRTC_PUBLIC_CANDIDATE` | Внешний host:port при поддержке tunnel |
| `STUN_SERVERS` | Необязательный список STUN |
| `TURN_URL` | Необязательный TURN |
| `TURN_USERNAME_FILE` | Секрет TURN |
| `TURN_CREDENTIAL_FILE` | Секрет TURN |
| `LOG_LEVEL` | Уровень без отладочного вывода секретов |

Параметры, которые не нужны выбранной реализации, не должны добавляться «про запас». Итоговый `.env.example` содержит только безопасные placeholders и никогда не содержит реальные секреты.

## 5. Первичный запуск

После появления реализации команды фиксируются в корневом README. Порядок операций:

1. Проверить поддержку Docker и Docker Compose.
2. Создать файлы секретов с безопасными случайными значениями.
3. Установить права `0600` на секреты.
4. Задать LAN address в `config/go2rtc.yaml` (`webrtc.candidates`) и public origin.
5. Собрать images.
6. Запустить миграции и сервисы.
7. Проверить healthchecks.
8. Войти как `admin`.
9. Добавить эталонную камеру.
10. Настроить OpenTunnel и выполнить T-15.

Пароль администратора применяется только при создании первичной записи. Последующий restart не сбрасывает пароль из файла bootstrap.

## 6. Healthcheck и restart

### Server

- Liveness: `/api/v1/health/live`.
- Readiness: `/api/v1/health/ready` только по внутреннему адресу server.
- Docker healthcheck вызывает server внутри Docker-сети. Caddy не публикует readiness.
- Restart policy перезапускает процесс после сбоя.

### Media

- Healthcheck использует узкий внутренний endpoint выбранной версии go2rtc.
- После restart media сервер выполняет Reconciliation.

### Web и proxy

- Web healthcheck запрашивает статический файл.
- Proxy healthcheck проверяет способность принимать HTTP без обращения к защищённым медиаданным.

Зависимости Compose не должны образовывать цикл. Server должен переживать запуск раньше media и повторять подключение.

## 7. Backup

Backup включает:

- SQLite с учётом WAL;
- `camera_encryption_key`;
- несекретные config-файлы;
- версии images и lock-файлы;
- при необходимости TURN configuration отдельно.

Backup не должен выполняться простым копированием только `.db`, пока активен WAL. Использовать SQLite backup API или согласованный snapshot всех SQLite-файлов.

Правила:

- Шифрованный backup хранится отдельно от production secrets по политике владельца.
- Для восстановления камер нужен именно исходный ключ шифрования.
- Потеря ключа требует повторного ввода паролей камер.
- Backup не включает активные admin sessions, если реализация умеет исключать их. После восстановления рекомендуется завершить все сессии.

## 8. Restore

Порядок:

1. Остановить запись в server.
2. Восстановить SQLite согласованным набором файлов.
3. Восстановить исходный `camera_encryption_key`.
4. Проверить права.
5. Запустить миграции только в поддерживаемом направлении.
6. Запустить сервисы.
7. Проверить Reconciliation.
8. Проверить одну камеру, снимок и ONVIF.

Downgrade SQLite на более старую версию приложения без отдельной миграции не поддерживается.

## 9. Обновление

Перед обновлением:

1. Создать backup.
2. Прочитать changelog server и go2rtc.
3. Проверить миграции.
4. Зафиксировать текущие версии для отката.

После обновления:

1. Проверить healthchecks.
2. Проверить список камер.
3. Проверить WebRTC и HLS.
4. Проверить JPEG и MJPEG.
5. Проверить PTZ и событие движения.
6. Проверить отсутствие новых секретов в логах.
7. После реализации этапа 2 проверить микрофон, audio playback, WAV для ИИ и отсутствие оставшихся FFmpeg-процессов.

Обновление go2rtc требует повторной проверки HLS routes. Caddy allowlist нельзя расширять до всего API ради устранения ошибки маршрута.

## 10. Логи и диагностика

- Docker logs доступны только администратору сервера.
- Уровень production по умолчанию — `INFO`.
- Debug включается временно.
- Перед включением debug нужно убедиться, что библиотека ONVIF не выводит пароли и SOAP userinfo.
- Логи не должны содержать тела auth, probe и camera update.
- Для диагностики используются request ID, camera ID, state и код ошибки.

Ротация Docker logs должна иметь конечный размер. Конкретный размер выбирается после получения объёма диска сервера.

## 11. Ресурсы

До получения CPU, RAM и архитектуры сервера нельзя задавать подтверждённые лимиты контейнеров.

Правила для целевой настройки:

- Не запускать видеотранскодирование H.264 по умолчанию.
- Ограничить MJPEG до 5 FPS и ширины 1280.
- Не допускать неограниченное число FFmpeg-процессов. Этап 2 ограничивает WAV capture одним процессом на камеру и двумя на server.
- Проверить главный экран с polling 1 секунда и очистку audio buffers после playback.
- Проверить RSS и число процессов в 60-минутном тесте.
- Проверить отсутствие постоянного роста памяти и descriptors.
- При нехватке CPU снизить FPS и ширину MJPEG, а не скрывать перегрузку.

Фактический замер (2026-11-22, T-17): 2 камеры Tapo C520WS, 2 зрителя WebRTC 2560×1440, 1 MJPEG 2 fps на камеру, 60 минут. server ≈0.03 ядра CPU / 155 МиБ RSS, media ≈1.4 ядра / 118 МиБ RSS, FFmpeg-процессы после остановки 0, дескрипторы стабильны. Подробности и CSV — `docs/verification.md` T-17. Это замер стенда владельца, не подтверждённые лимиты контейнеров.

## 12. Смена и восстановление секретов

### Bearer-токен ИИ

Смена токена требует обновления секрета и restart server. Старый токен должен перестать работать. Нужно обновить конфигурацию ИИ-агента.

### Пароль администратора

MVP может предоставлять recovery через локальную административную команду. Команда должна требовать доступа к host, не выводить пароль в историю shell и завершить активные сессии. До реализации команды нельзя считать recovery готовым.

### Ключ камер

Ротация ключа не входит в MVP. Смена ключа без перешифрования делает сохранённые пароли камер нечитаемыми. Такая операция должна быть запрещена конфигурацией или сопровождаться явной процедурой повторного ввода секретов.

## 13. Критерии готовности deployment

- Fresh install проходит по документированным шагам.
- Restart сохраняет камеры и не создаёт дубликаты потоков.
- Backup и restore проверены на копии данных.
- Наружу открыты только разрешённые порты.
- Все секреты отделены от images и репозитория.
- Логи имеют ротацию и не содержат секреты.
- Нагрузочный тест выполнен на целевом сервере или явно отмечен как не выполненный.
